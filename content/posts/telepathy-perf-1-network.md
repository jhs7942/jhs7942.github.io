> 2편 시리즈입니다. **(1/2) 네트워크 편(이 글)** · (2/2) 렌더링·로드 편

텔레파시는 **15초마다 열리는 라운드에서 같은 단어를 고른 두 사람을 이어주는 실시간 매칭 서비스**입니다. React 19 + Vite SPA 프런트엔드와 Express + Supabase 백엔드로 구성한 사이드 프로젝트입니다.

이 글은 그 프로젝트에 세 라이브러리를 도입하기 전, 현재 상태를 숫자로 먼저 기록한 과정을 다룹니다. "도입했다"는 사실보다 "얼마나 나아졌는지"가 중요합니다. 그 말을 하려면 도입 전 기준치가 있어야 합니다. 그래서 순서를 뒤집었습니다 — 문제가 있을 법한 지점 6개를 먼저 정하고, 각각 측정하고, 숫자를 근거로 도입 여부를 결정했습니다.

결과를 미리 보면:

- 라이브러리 **2개 도입, 1개 취소**

- 기각된 가설 **3개**

- 가장 큰 문제는 **세 라이브러리 중 무엇도 해결하지 못하는 지점**에서 나왔습니다

이번 편에서는 **Network 탭으로 측정한 3개 지점**(중복 요청·연타·폴링)을 다룹니다. 리렌더와 로드 측정, 그리고 뒤바뀐 계획은 2편에 있습니다.

## 측정 도구를 먼저 정했습니다

처음에는 Jest + RTL로 성능을 측정하려 했습니다. 조사 후 포기했습니다. **jsdom에는 레이아웃 엔진이 없습니다.** 브라우저가 실제로 화면을 그리는 비용이 빠진 숫자는 실제 성능과 상관관계가 없고, "jsdom으로 성능을 쟀다"는 측정 방법 자체에 문제가 생깁니다. 테스트는 리팩터링 회귀 안전망으로만 사용하기로 했습니다.

성능은 계층별로 브라우저 도구를 사용했습니다.

| 계층 | 도구 | 측정 항목 |
| :---: | :---: | :---: |
| 네트워크 | DevTools Network | 요청 몇 건, 얼마나 오래 걸리나 |
| 렌더링 | React DevTools Profiler | 화면을 몇 번 다시 그렸나(commit) |
| 로드 | Lighthouse | 사용자가 첫 화면까지 얼마나 기다리나 |

세 도구를 간략히 설명하면, **DevTools Network**는 브라우저 개발자 도구의 Network 패널로 앱이 보내는 HTTP 요청 수·걸린 시간·응답 크기를 기록합니다. **React DevTools Profiler**는 React 컴포넌트가 화면을 다시 그릴 때마다 기록하는 분석 도구이며, 여기서 **commit**은 React가 변경 사항을 실제 DOM에 반영하는 순간을 뜻합니다. **Lighthouse**는 Chrome에 내장된 성능 감사 도구로, FCP·LCP 같은 사용자 체감 로드 지표를 자동으로 측정합니다.

측정 조건은 고정했습니다: **프로덕션 빌드, 시크릿 창, Fast 4G + CPU 4x 스로틀, 모바일 뷰포트, 3회 중앙값.** 조건이 달라지면 before/after 비교가 성립하지 않습니다.

예외가 하나 있습니다. Profiler는 프로덕션 빌드에서 동작하지 않아, 리렌더 측정만 dev 서버에서 진행했습니다. **리렌더 횟수는 dev와 prod가 동일**하므로 측정은 유효하고, 시간 값만 참고용으로 봤습니다.

원칙 두 가지를 미리 정했습니다.

1. **한 번에 하나씩 바꾸고 매번 재측정합니다** — 동시에 바꾸면 무엇이 효과였는지 증명할 수 없습니다.

2. **가설이 재현되지 않아도 그대로 기록합니다** — 이 원칙이 나중에 계획을 바꾸게 됩니다.

## 화면을 오갈 때마다 같은 데이터를 다시 받습니다

모든 데이터 요청이 이 패턴으로 작성되어 있습니다.

```tsx
useEffect(() => {
  fetch('/api/word-history') ...
}, []);
```

React에는 데이터 캐시가 없습니다. 컴포넌트가 마운트될 때마다 fetch가 다시 실행되고, 방금 받은 데이터를 기억할 곳이 없습니다.

페이지 A ↔ B를 두 번 왕복하며 요청을 기록했습니다. **API 요청 15건 중 8건이 중복이었습니다.** 같은 목록 데이터를 4번, 로그인 확인을 4번 받았습니다. 사용자 입장에서는 이미 받은 목록을 화면을 이동할 때마다 다시 기다려야 하고, 네트워크가 느릴수록 이 대기가 쌓입니다.

흥미로운 건 비용의 정체였습니다. 응답이 0.3~0.4 kB로 매우 작은데 요청당 **180 ms**가 걸렸습니다. **비용은 데이터 크기가 아니라 왕복 지연입니다.** 서버가 원격 DB(Supabase)를 다시 호출하니, 요청 1건에 왕복이 2번 겹칩니다. 페이로드를 줄이는 것이 아니라 **요청 자체를 없애는 캐싱**이 정확한 해법입니다. → **TanStack Query 도입 근거 ①**

## 하트를 연속으로 누르면 클릭 수만큼 요청이 나갑니다

즐겨찾기 하트는 **낙관적 업데이트**(서버 응답을 기다리지 않고 화면을 먼저 바꾼 뒤 나중에 서버 결과를 반영하는 패턴) 후 PATCH를 보내는 방식입니다. 체감 반응 속도를 높이지만, 서버가 실패하면 화면을 되돌려야 합니다.

취소 로직도 직렬화도 없어서 **6번 클릭 = 6번 요청**입니다. 최종 저장값은 하나뿐이니, **5건(83%)은 곧바로 덮어써질 값을 쓰기 위한 낭비**입니다. Slow 4G 환경에서는 이 낭비가 3초를 넘겼습니다.

더 주목했던 건 **경쟁 상태(Race Condition)**였습니다. 응답 순서가 뒤집히면 UI와 DB의 상태가 어긋날 수 있습니다. 회선을 늦춰가며 6회 시도했는데 — **0회 재현**이었습니다.

**워터폴**(Network 탭에서 각 요청의 시작·진행·완료 시점을 가로 막대로 보여주는 그래프)을 확인했습니다. 요청들이 완전히 동시에 나가지 않고 계단식으로 어긋나 있었습니다. 사람의 연타 간격(~580 ms)이 응답 시간(~600 ms)과 비슷하고, **HTTP/1.1 연결 제한**(HTTP/1.1이 도메인당 동시 연결 수를 6개 내외로 제한하는 규칙)이 요청을 자연스럽게 줄 세운 것으로 추정됩니다.

여기서 기록 방식이 중요합니다. **"미재현"과 "안전"은 다릅니다.** 응답 편차가 크거나 HTTP/2 환경이면 언제든 발생할 수 있습니다. 그래서 "현재 조건에서 미재현"으로 조건을 명시해 기록했습니다. → **TanStack Query 도입 근거 ② (`useMutation` 직렬화 + 스냅샷 롤백)**

## 아무것도 하지 않아도 1분에 59번 요청합니다

메인 화면은 라운드 남은 시간을 서버와 맞추기 위해 1초마다 서버에 물어봅니다. 이처럼 클라이언트가 일정 간격으로 반복해서 서버에 묻는 방식을 **폴링(Polling)**이라 합니다. 구현은 단순하지만, 화면에 머무는 시간에 비례해 요청이 쌓입니다.

아무 조작 없이 60초를 기다린 결과: **59건**이었습니다.

앞의 두 문제와 성격이 다릅니다. 1번과 2번은 사용자 행동에 비례하지만, **폴링은 화면에 머무는 시간에 비례하고 상한이 없습니다.** 사용자 100명이 10분 머물면 59,000 요청입니다.

측정하다 더 위험한 지점을 발견했습니다. 발사 간격 1,000 ms vs 응답 시간 587 ms — `setInterval`은 이전 요청의 완료를 기다리지 않습니다. 응답이 1초를 넘기는 순간 요청이 겹쳐 쌓이기 시작합니다. 실제로 마지막 요청이 `(pending)` 상태인 장면이 기록됐습니다.

그리고 **첫 번째 가설 기각**이 나왔습니다. "백그라운드 탭에서도 계속 요청할 것"이라 예상하고, 탭을 전환해 60초를 측정했습니다 — **0건**이었습니다. 브라우저가 비활성 탭의 타이머를 이미 **스로틀링**(일정 시간 내 실행 횟수를 자동으로 제한하는 기법)하고 있었기 때문입니다.

`refetchIntervalInBackground` 같은 옵션이 이 앱에서 개선 근거가 될 수 없는 이유입니다. 브라우저가 이미 처리하고 있는 일을 별도 개선으로 주장할 수 없습니다.

## 세 지표가 가리킨 것

네트워크 측정 3개를 정리하면 다음과 같습니다.

| 지점 | 측정 결과 | 사용자 영향 |
| :---: | :---: | :---: |
| 중복 요청 | 15건 중 8건(53%) 중복 | 이미 받은 데이터를 화면 전환마다 다시 기다림 |
| 하트 연타 | 6클릭 = 6요청, 5건(83%) 낭비 | Slow 4G에서 불필요한 3초 대기 |
| 폴링 | 분당 59건, 상한 없음 | 체류 시간에 비례해 서버 부하 누적 |

세 지점 모두 같은 진단을 내립니다. 이 앱은 **요청을 만들 줄만 알고, 관리하지 않습니다.** 캐시가 없어 중복이 생기고, 직렬화가 없어 연타가 그대로 나가고, 완료 확인 없이 폴링이 겹칩니다.

셋 다 TanStack Query가 겨냥하는 지점이라, **도입은 여기서 확정됐습니다.**

## 핵심 정리

- **중복 요청의 비용은 페이로드가 아니라 왕복 지연입니다.** 응답이 0.4 kB여도 요청당 180 ms가 걸리는 이유는, 서버가 원격 DB를 다시 호출하기 때문입니다. 페이로드 최적화가 아닌 캐싱이 정확한 해법입니다.

- **폴링은 사용자 행동과 무관하게 쌓입니다.** 상한이 없는 요청은 사용자 수와 체류 시간에 따라 선형으로 증가합니다.

- **"미재현"과 "안전"은 다릅니다.** 경쟁 상태를 6회 시도해 0회 재현했더라도, 환경 조건을 명시해 기록해야 합니다.

- **브라우저가 이미 해결한 문제를 개선으로 주장하면 안 됩니다.** 백그라운드 탭 폴링 0건은 브라우저의 타이머 스로틀 덕분이었습니다.

- **한 번에 하나씩 바꾸고 매번 재측정해야 합니다.** 동시에 여러 변경을 적용하면 무엇이 효과였는지 분리할 수 없습니다.

2편에서는 React DevTools Profiler로 리렌더를 측정합니다. 거기서 **도입 예정이던 라이브러리 하나가 취소**되고, Lighthouse에서 **계획에 없던 진짜 범인**을 마주하게 됩니다.
