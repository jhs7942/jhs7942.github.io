## 🧭 1. 두 가지 전략이란?
- **점진적 수정(Fix-one → Test → Repeat)** — 에러 하나 수정 후 테스트 실행, 결과 확인 후 다음 에러로 이동하는 방식. 피드백 루프가 짧지만 사이클 수가 많아집니다.

- **일괄 수정(Analyze-all → Fix-all → Test)** — 전체 실패를 수집하고 소스 코드까지 읽어 근본 원인을 분류한 뒤, 한번에 수정하고 테스트하는 방식. 초기 분석 시간이 더 걸리지만 총 사이클 수가 적습니다.

## ⚖️ 2. 전략 비교
| 항목 | 점진적 수정 | 일괄 수정 |
| :---: | :---: | :---: |
| 피드백 루프 | 짧음 | 길음 (초기 분석) |
| 총 사이클 수 | 많음 | 적음 |
| 근본 원인 파악 | 늦어질 수 있음 | 초기에 파악 |
| 수정 간 충돌 감지 | 조기 발견 | 한꺼번에 드러남 |
| 적합한 상황 | 에러가 독립적일 때 | 소수 원인에서 다수 실패가 파생될 때 |

## 📊 3. 실제 사례 비교 (Playwright 22개 테스트, 13개 실패)

### 실제 진행 (점진적, 비효율)
```text
12회 테스트 실행, ~80분 소요
증상 치료 → 새 증상 발생 → 되돌리기 반복
workers:1 적용 → 오히려 3개 추가 실패 → 되돌림
UrlNormalizer 발견은 7번째 반복에서
```

### 이상적 접근 (일괄, 추정)
```text
1회: 실패 목록 수집
소스 코드 읽기 (10분): UrlNormalizer, session.ts, splash 발견
전체 수정 후 2회: 검증
잔여 이슈 수정 후 3회: 최종 확인
총 ~25분
```

- 80분 vs 25분 — 소스 코드를 10분 더 읽는 것이 전체 시간을 대폭 절약합니다.

## 🧭 4. 상황별 전략 선택 기준
| 상황 | 적합한 방식 | 이유 |
| :---: | :---: | :---: |
| 다수 실패가 소수 근본 원인에서 파생 | 일괄 | 원인 하나 잡으면 여러 실패가 동시 해결 |
| 에러들이 서로 독립적 | 점진적 | 각 수정이 다른 에러에 영향 없음 |
| 코드베이스를 잘 모름 | 점진적 | 테스트 결과가 코드 이해를 도움 |
| 수정 간 충돌 가능성 | 점진적 | 충돌을 조기 발견 |
| 코드베이스를 충분히 이해 | 일괄 | 분석 정확도가 높으므로 한번에 처리 가능 |

## ✅ 5. 수정 전 체크리스트
1. 이 실패의 **근본 원인**을 알고 있는가? (모르면 소스 코드부터 읽기)

2. 여러 실패가 **같은 원인**에서 나온 것 같은가? (그러면 일괄 수정)

3. 이 수정이 **다른 테스트에 영향**을 줄 수 있는가? (그러면 점진적)

4. 수정 후 결과를 **예측할 수 있는가?** (예측 가능하면 일괄, 불확실하면 점진적)

## ✅ 6. 핵심 정리
- **근본 원인 분석에 투자한 시간 ∝ 절약되는 수정-테스트 사이클 수**

- 증상을 바로 고치고 싶은 유혹이 있지만, 소스 코드를 먼저 읽는 습관이 중요합니다

- 다수 실패 + 소수 근본 원인 패턴에서는 일괄 수정이 압도적으로 효율적입니다

- 코드베이스 이해도가 낮을 때는 점진적 수정으로 학습하면서 진행하는 것이 안전합니다
