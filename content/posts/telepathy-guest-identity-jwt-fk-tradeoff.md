텔레파시의 사용 흐름은 짧습니다. 접속하고, 단어를 고르고, 15초 안에 누군가와 연결됩니다. 이 흐름 앞에 회원가입을 세우면 서비스의 성격 자체가 무너집니다. "가볍게 익명으로 대화한다"는 제안에 아이디와 비밀번호를 요구하는 셈이기 때문입니다.

그래서 가입 없이 쓸 수 있어야 했습니다. 문제는 그다음이었습니다.

---

## 🔍 1. 익명이라고 신원이 필요 없는 건 아니다

기능을 하나씩 뜯어보니 전부 신원을 전제하고 있었습니다.

| 기능 | 필요한 것 |
|------|----------|
| 매칭 | 큐에서 나와 상대를 구분할 식별자 |
| 채팅 | 메시지 발신자 판별 |
| 신고 | 누가 누구를 신고했는지 |
| 재선택 | 같은 라운드에서 내 기존 대기를 찾아 지우기 |

즉 "익명"은 **다른 사용자에게** 익명이라는 뜻이지, **시스템에게까지** 익명이라는 뜻이 아니었습니다. 서버는 이 사람이 누구인지 알아야 하고, 다만 그 정보가 실명과 연결되지 않을 뿐입니다.

정리하면 요구사항은 이랬습니다.

> 가입 절차 없이, 시스템이 식별 가능하고, 세션 간 유지되는 신원

---

## 🤔 2. 교과서적 답과 그에 대한 의심

일반적인 해법은 명확합니다. `users` 테이블에 게스트 행을 만들고 `is_guest` 플래그를 세우는 것입니다. FK도 정상적으로 걸리고, 구조도 깔끔합니다.

그런데 기존 `users` 스키마를 보니 걸리는 점이 있었습니다.

- `username`이 유니크 제약을 갖는다 → 게스트마다 가짜 유니크 값을 만들어야 한다
- `password_hash`가 있다 → 비밀번호 없는 사용자에게 무엇을 넣을 것인가
- 방문자마다 행이 하나씩 생긴다 → 이탈한 게스트 행을 언제 어떻게 지울 것인가

게스트를 `users`에 넣는다는 건 **회원을 전제로 설계된 테이블에 회원이 아닌 것을 밀어넣는 일**이었습니다. 그러려면 가짜 값이 필요하고, 가짜 값이 들어가는 순간 그 컬럼의 의미는 흐려집니다.

## 🔑 3. 신원을 DB가 아니라 토큰에 둔다

게스트를 `users`에 저장하지 않기로 했습니다. 대신 신원 전체를 JWT 안에 담았습니다.

```ts
// 게스트 세션 발급 (멱등)
router.post('/guest', (req: Request, res: Response) => {
  const existing = decodeToken(req.cookies?.token);

  if (existing?.role === 'guest') {
    // 이미 게스트면 같은 신원 유지
    return res.json({
      success: true,
      user_id: existing.user_id,
      nickname: existing.nickname || GUEST_NICKNAME,
      role: 'guest',
    });
  }

  if (existing?.role === 'member') {
    // 회원 토큰을 게스트로 덮어쓰지 않는다
    return res.status(409).json({
      success: false,
      message: '이미 회원 세션이 활성화되어 있습니다.',
    });
  }

  const guestId = uuidv4();
  const token = jwt.sign(
    { user_id: guestId, nickname: GUEST_NICKNAME, role: 'guest' },
    process.env.JWT_SECRET as string,
    { expiresIn: '7d' },
  );
  res.cookie('token', token, buildCookieOptions(1000 * 60 * 60 * 24 * 7));
  // ...
});
```

판단 근거는 세 가지였습니다.

**첫째, 진입 시 DB 쓰기가 0회입니다.** 게스트 발급은 uuid 생성과 토큰 서명뿐입니다. 방문자가 늘어도 테이블은 커지지 않습니다.

**둘째, 정리할 것이 없습니다.** 이탈한 게스트를 지우는 배치가 필요 없습니다. 토큰이 만료되면 그대로 사라집니다.

**셋째, 서버 상태가 아닙니다.** 서버가 재시작해도 신원은 클라이언트 쿠키에 남아 있습니다.

### 결정을 끝까지 밀고 간다 — 닉네임 변경도 재서명으로

여기서 타협하기 쉬운 지점이 있었습니다. 닉네임 변경입니다. "닉네임 정도는 DB에 두자"고 하면 신원의 출처가 둘로 갈라집니다.

그래서 닉네임 변경도 DB를 쓰지 않고, `user_id`는 유지한 채 토큰을 다시 서명하도록 했습니다.

```ts
// user_id는 유지하고 nickname만 갱신해 재서명
const token = jwt.sign(
  { user_id: existing.user_id, nickname: clean, role: 'guest' },
  process.env.JWT_SECRET as string,
  { expiresIn: '7d' },
);
```

**토큰이 신원의 단일 출처**라는 원칙을 지킨 것입니다. 게스트 발급 요청을 멱등하게 만든 것도, 회원 토큰이 있을 때 409로 거절한 것도 같은 맥락입니다. 발급 요청이 여러 번 와도 신원이 바뀌지 않아야 하고, 회원이 실수로 게스트로 강등되면 안 됩니다.

## 🧩 4. 검증 지점을 하나로 모은다

신원 종류가 둘로 늘면 검증 코드가 갈라지기 쉽습니다. HTTP는 미들웨어에서 확인하고 소켓은 소켓대로 확인하는 식이면, 나중에 인증을 고칠 때 두 곳을 봐야 합니다. 이 프로젝트는 REST API와 Socket.IO를 함께 쓰기 때문에 위험이 컸습니다.

그래서 토큰 해석 함수를 하나만 두고, HTTP 미들웨어와 소켓 `io.use`가 그 함수를 공유하도록 했습니다.

```ts
// 토큰 해석 — HTTP 미들웨어와 소켓 io.use가 공유
export function decodeToken(token?: string): SessionUser | null {
  if (!token) return null;
  try {
    const decoded = jwt.verify(token, process.env.JWT_SECRET as string);
    if (typeof decoded !== 'object' || decoded === null) return null;

    // 하위 호환: role이 없는 기존 토큰은 member로 간주
    const role = decoded.role === 'guest' ? 'guest' : 'member';

    return role === 'guest'
      ? { user_id: ..., nickname: ... || GUEST_NICKNAME, role }
      : { user_id: ..., username: ..., role };
  } catch {
    return null;
  }
}
```

이 함수 위에 권한 레벨을 얇게 쌓았습니다.

| 미들웨어 | 허용 | 사용처 |
|---------|------|--------|
| `requireMember` | 회원만 | 결제, 확성기, 마이페이지 |
| `requireSession` | 회원 + 게스트 | 신고, 피드백 |

기능마다 "게스트도 되나?"를 판단하는 대신 **둘 중 하나를 고르는 문제**로 바꾼 것입니다.

### 기존 토큰을 무효화하지 않기

게스트를 도입하는 시점에 이미 발급된 회원 토큰들이 있었습니다. 그 토큰에는 `role`이 없습니다. 엄격하게 검사하면 기존 사용자가 전부 로그아웃됩니다.

그래서 `role`이 없는 토큰은 member로 간주했습니다. `decoded.role === 'guest'`인 경우만 게스트로 보고, 나머지는 전부 회원으로 처리합니다. 새 필드를 추가하면서 기존 토큰을 깨지 않는 방향을 택한 것입니다.

### 신원은 서버가 확정한다

검증 지점을 하나로 모으면 신원을 확정하는 위치도 하나가 됩니다. 소켓 핸들러는 클라이언트가 보낸 값 대신 서버가 확정한 값을 씁니다.

```ts
// 게스트는 토큰 닉네임, 회원은 payload 닉네임
const nickname = isGuest ? me.nickname || GUEST_NICKNAME : data.nickname;
const username = isGuest ? userId : (me.username ?? userId);
```

게스트 닉네임을 payload가 아니라 토큰에서 가져오는 이유가 있습니다. 게스트는 서버에 저장된 프로필이 없으므로, payload를 믿으면 아무 닉네임이나 실어 보낼 수 있습니다. 반면 회원은 DB에 프로필이 있어 대조가 가능합니다. 같은 이유로 메시지 브로드캐스트도 서버가 신원을 덮어쓴 뒤 내보냅니다.

## 🧾 5. 대가 — FK를 걸 수 없다

이 결정에는 분명한 대가가 있었습니다. **게스트는 `users`에 행이 없으므로 어떤 테이블도 게스트를 FK로 참조할 수 없습니다.**

파장은 세 곳으로 번졌습니다.

**하나. 게스트 본인은 단어장을 가질 수 없습니다.** `word_history`는 `user_id`가 `users`를 참조합니다. 게스트 행이 없으니 저장 자체가 불가능합니다.

**둘. 상대가 게스트면 `partner_id`를 null로 둡니다.** 회원이 게스트와 매칭됐을 때, 회원의 기록에는 남겨야 하는데 참조할 대상이 없습니다. 그래서 `partner_id`는 null로 두고 닉네임만 남겼습니다.

```ts
// · 게스트 본인 기록은 users 에 행이 없어 FK 제약상 저장 불가 → 제외
// · 상대가 게스트면 partner_id 는 null 로 두고 닉네임만 남긴다
// · 같은 상대 + 같은 단어 조합은 한 번만 남긴다
```

**셋. 큐에서 게스트를 간접 추론합니다.** `telepathy_sessions_queue`에는 role 컬럼이 없습니다. 게스트는 username에 user_id(uuid)를 그대로 넣으므로, 두 값이 같으면 게스트로 판별합니다.

```ts
// 큐에 role 컬럼이 없어 저장된 값으로 판별한다.
// 게스트는 username에 user_id(uuid)를 그대로 넣으므로 두 값이 같다.
const partnerIsGuest = partner.username === partner.user_id;
```

명시적 플래그가 아니라 **데이터 형태로 판별하는 것이라 취약합니다.** 알고 있고, 문서에 남겨뒀습니다.

### 대가가 쿼리 작성법까지 바꿨다

`partner_id`가 null일 수 있게 되자 중복 검사 로직이 갈라졌습니다.

```ts
// partner_id 가 null(게스트 상대)이면 = 비교가 안 되므로 IS NULL + 닉네임으로 판별
query =
  record.partner_id === null
    ? query.is('partner_id', null).eq('partner_nickname', record.partner_nickname)
    : query.eq('partner_id', record.partner_id);
```

SQL의 3값 논리 때문에 `NULL = NULL`은 참이 아니라 UNKNOWN입니다. `.eq()`로는 null 행을 절대 잡지 못하므로 `.is()`를 써야 합니다.

이건 프로젝트 컨벤션 문서에 팀 규칙으로 올려뒀습니다. 한 번 겪은 함정을 개인 기억이 아니라 문서에 남기기 위해서입니다.

## ⚠️ 6. 인정해야 하는 한계

**게스트 상대는 동일인 판정이 불가능합니다.** 닉네임으로 판별하므로, 같은 닉네임을 쓰는 서로 다른 게스트 둘은 한 사람으로 합쳐집니다. 반대로 엄격하게 가면 같은 사람과 여러 번 만났을 때 중복이 쌓입니다.

이건 기술로 풀 수 없는 문제라고 판단했습니다. 익명 서비스에서 "같은 사람"은 정의 자체가 불가능합니다. 단어장은 정확한 통계가 아니라 "이런 단어로 누군가와 만났다"는 경험을 남기는 기능이므로, 중복이 쌓이는 쪽보다 가끔 합쳐지는 쪽을 택했습니다.

**게스트 신원은 쿠키를 지우면 사라집니다.** 만료도 7일입니다. 이건 방어하지 않기로 했습니다. 게스트에게 영속성을 약속하지 않는 것이 제품 의도와도 맞기 때문입니다. 기록을 남기고 싶으면 가입하면 됩니다.

---

## 💡 7. 의도하지 않았던 결과

구현을 마치고 나서야 알아차린 게 있습니다. **기술 제약에서 나온 비대칭이 제품 정책이 되어 있었습니다.**

```
게스트  → 기록을 갖지 못한다
회원    → 게스트와의 만남도 기록에 남는다
```

가입하면 인연이 남습니다. 회원 전환의 이유가 하나 생긴 셈입니다.

분명히 해두면, **이건 설계 의도가 아니라 사후 발견입니다.** FK 제약을 피하다 보니 그렇게 된 것이고, 결과적으로 제품에 유리했을 뿐입니다. 다만 이 경험에서 배운 것은 있습니다. 기술적 제약이 항상 손해로만 끝나지는 않으며, 제약이 만든 구조를 제품 관점에서 다시 읽어볼 필요가 있다는 것.

## ✅ 8. 상환 계획과 남는 생각

부채인 것은 분명하므로 갚을 계획을 세워뒀습니다.

| 기존 | 신규 |
|------|------|
| `users` | `actors` + `users` + `user_credentials` |

회원과 게스트가 `actors`의 공통 식별자를 갖고, 인증 정보는 `user_credentials`로 분리합니다. 게스트도 `actors`에 행이 생기므로 FK를 정상적으로 걸 수 있고, 게스트에서 회원으로 전환할 때 기존 기록을 승계할 수 있습니다. 앞서 언급한 세 가지 파장이 한꺼번에 해소되는 구조입니다.

이 작업에서 가장 오래 고민한 건 코드가 아니라 **어디까지 미룰 것인가**였습니다.

처음부터 `actors` 구조로 갔다면 부채는 없었을 것입니다. 하지만 그러려면 인증 체계 전체를 다시 설계해야 했고, 그 시점에 필요한 건 "게스트도 쓸 수 있는가"를 빨리 확인하는 일이었습니다.

정규화를 미루는 선택 자체보다 중요한 건 그다음이라고 생각합니다. 미룬 것을 미뤘다고 기록해두는 것, 그 부채가 어디로 번지는지 추적하는 것, 그리고 갚을 시점과 방법을 정해두는 것.
