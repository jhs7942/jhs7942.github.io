개발 플로우를 자동화하면 코드는 알아서 굴러가는데 이슈 보드만 사람이 따라다니게 됩니다. 기획이 끝나면 이슈를 만들고, 구현에 들어가면 상태를 옮기고, 리뷰에서 결함이 나오면 하위 이슈를 쪼개는 일이 전부 손입니다. 이 구간을 파이프라인 안으로 넣으려고 Linear MCP를 연동했습니다.

세 가지를 확인하고 싶었습니다. 개발 플로우가 진행되면서 Linear를 자동으로 고칠 수 있는가, 남의 워크스페이스에 초대됐을 때도 되는가, 그리고 반대 방향 — 팀원이 Linear를 고쳤을 때 그걸 로컬 진행 상태에 반영할 수 있는가.

앞의 둘은 금방 됐습니다. 시간이 걸린 건 세 번째였습니다.

## 📦 1. 붙이기 전에 확인한 것 — upsert와 identifier

Linear MCP는 원격 HTTP MCP 서버(`https://mcp.linear.app/mcp`)로 OAuth 인증을 씁니다. 플러그인 설치 → `/mcp` 인증 → 도구 노출의 3단계를 거치면 도구 32종이 세션에 붙습니다.

붙자마자 코드를 짜는 대신 샌드박스 팀을 하나 만들어 도구를 직접 호출해봤습니다. 문서만 보고 설계하면 나중에 뒤집힙니다.

**`save_*` 하나가 생성과 수정을 겸합니다.** GitHub API의 `create_*`/`update_*` 분리 구조를 예상했는데 달랐습니다.

```
save_issue(team="CDS", title="...")     → id 없음 → create
save_issue(id="CDS-42", state="...")    → id 있음 → update
```

에이전트 입장에서는 이게 편합니다. "이슈가 이미 있는가"를 먼저 조회하지 않아도 되고, 같은 훅이 두 번 돌아도 `id`만 들고 있으면 중복 생성이 안 납니다. 멱등성을 공짜로 얻는 셈입니다.

**응답의 `id`가 UUID가 아니라 identifier였습니다.** 이건 예상 밖이었습니다.

- 내부 UUID(`bc1fe577-…`)가 아니라 `CDS-1` 형태를 돌려줍니다.

- 모든 도구가 identifier를 그대로 받습니다.

- 즉 **UUID를 따로 조회해 들고 다닐 필요가 없습니다.** 진행 상태 파일에 `CDS-1`만 적어두면 됩니다.

사람이 읽을 수 있는 값이 그대로 키가 되니, 로그와 진행 파일이 훨씬 읽기 쉬워졌습니다.

## 🔍 2. 라벨은 덮어쓰기, 관계는 추가

여기가 이 글에서 제일 중요한 부분입니다. 모르고 지나가면 라벨이 조용히 사라집니다.

Phase가 바뀔 때마다 `phase/ideate` → `phase/design`처럼 라벨을 갈아 끼워야 했습니다. 그래서 "바뀐 라벨만 넘기면 되겠지" 하고 짰다가 스모크 테스트에서 걸렸습니다.

```
# 이전 상태
labels = ["type/feat", "priority/medium", "phase/ideate"]

save_issue(id="CDS-1", labels=["type/feat", "priority/medium", "phase/design"])

# 결과
labels = ["type/feat", "priority/medium", "phase/design"]
# phase/ideate 사라짐 → 완전 덮어쓰기 확정
```

`labels`는 **넘긴 배열로 통째로 교체**됩니다. 만약 `labels=["phase/design"]`만 넘겼다면 `type/feat`과 `priority/medium`까지 같이 날아갔을 겁니다. 에러도 안 납니다. 그냥 조용히 없어집니다.

그런데 같은 API 안에서 관계 필드는 반대로 동작합니다.

- **`labels` — replace.** 넘긴 배열이 곧 최종 상태입니다.

- **`blocks` · `blockedBy` · `relatedTo` · `links` — append-only.** 넘긴 값이 기존 목록에 덧붙습니다.

같은 `save_issue` 호출 안에서 필드마다 병합 규칙이 다른 겁니다. 이 비대칭을 모르면 두 방향으로 다 틀립니다. 라벨은 의도치 않게 지워지고, 관계는 지우려다 중복으로 쌓입니다.

그래서 Phase 전환 로직을 **"현재 라벨 전체를 읽어와 `phase/*`만 치환한 새 배열을 만들어 통째로 넘긴다"**로 바꿨습니다. 부분 갱신처럼 보이는 작업이지만 실제로는 매번 전체를 재구성합니다.

## 🛠️ 3. Phase와 워크플로 상태를 잇기

개발 파이프라인의 Phase를 Linear의 워크플로 상태에 대응시켰습니다.

| Phase | Linear state | state type |
| :---: | :---: | :---: |
| ideate | Backlog | backlog |
| design | Todo | unstarted |
| implement | In Progress | started |
| review | In Review | started |
| docs | In Progress (재사용) | started |
| done | Done | completed |
| cancelled | Canceled | canceled |

문제는 이 이름이 팀마다 다르다는 점입니다. 어떤 팀은 `In Review`가 없고, 어떤 팀은 `Shipped`를 씁니다. 이름을 하드코딩하면 남의 워크스페이스에 초대되는 순간 깨집니다.

그래서 3단 퍼지 매칭을 넣었습니다.

- **1단 — 이름 정확 일치.** `In Review`가 있으면 그대로 씁니다.

- **2단 — state type 기반.** 이름이 없으면 `started` 타입 중 두 번째를 리뷰로 잡습니다. Linear는 모든 상태에 `backlog`/`unstarted`/`started`/`completed`/`canceled` 타입을 강제하므로 이 축은 항상 존재합니다.

- **3단 — 라벨 fallback.** 그것도 안 되면 상태 대신 `phase/*` 라벨로만 구분합니다.

부트스트랩은 이 매핑과 필수 라벨 16종을 한 번에 만들고, 결과를 진행 상태 파일과 캐시에 적어둡니다. 멱등하게 짜서 두 번 돌려도 이미 있는 라벨은 건너뜁니다. 실제 로그에도 `16 required labels verified, 0 created`로 찍혔습니다.

## ⚙️ 4. 역방향이 어려웠다 — 네 가지 버킷

정방향(플로우 → Linear)은 단순합니다. 어려운 건 반대입니다. 팀원이 Linear에서 직접 뭔가 바꿨을 때 그걸 로컬에 어떻게 반영할 것인가.

두 극단이 다 나쁩니다. **전부 자동 반영하면** 사람이 판단해야 할 변경까지 덮어씁니다. **매번 물으면** 승인 피로가 쌓여서, 결국 내용을 안 보고 y를 누르게 됩니다. 승인 절차가 있으나 마나 해집니다.

그래서 변경을 성격별로 4가지로 나눴습니다.

| 버킷 | 내용 | 처리 | 파일 수정 |
| :---: | :---: | :---: | :---: |
| **blocking** | 이슈 취소·차단 | 진행 즉시 중단 + 강제 질문 | X |
| **mechanical** | state · labels · priority · assignee | 일괄 승인 1회 후 반영 | O |
| **textual** | 제목 · 본문 · 코멘트 | 알림만 | X |
| **structural** | 부모 변경 · 신규 하위 이슈 | 알림만 | X |

원칙은 세 가지입니다.

- **기계적 변경만 자동 반영합니다.** 텍스트와 구조 변경은 절대 자동으로 파일을 고치지 않습니다. 사람이 읽고 판단할 영역입니다.

- **승인은 묶어서 한 번만 묻습니다.** mechanical이 몇 건이든 질문은 1회입니다. 건별로 물으면 피로가 쌓여 승인이 형식이 됩니다.

- **에이전트는 사용자와 직접 대화하지 않습니다.** 충돌이 나면 오케스트레이터로 올려서 3지 선택(로컬 우선 / 원격 우선 / 건너뛰기)을 받고, 그 결정을 파라미터에 담아 다시 호출합니다. 에이전트는 판단 데이터만 만들고 대화는 상위에서 처리합니다.

비용도 신경 썼습니다. 원격 스냅샷의 해시가 직전과 같으면 차이 계산을 시작하기 전에 그냥 끝냅니다. 아무것도 안 바뀐 흔한 경우에 비용이 0이 됩니다.

## ⚠️ 5. 검증했더니 구멍이 네 개였다

설계를 끝내고 샌드박스에서 전 구간을 돌렸습니다. 이슈 생성 → Phase 전환 2회 → 종료, 그리고 외부에서 이슈를 고친 뒤 역방향 감지까지. 로그에는 이렇게 찍혔습니다.

```
sync_state | 5 drifts detected: state, priority, labels
pull       | 코멘트 1건 확인 → 진행 상태 파일 4필드 갱신
```

돌아는 갔습니다. 그런데 로그를 뜯어보니 설계에 구멍이 4개 있었습니다.

**치명적인 것 둘입니다.**

- **감지는 하는데 저장을 안 했습니다.** 반영 대상 필드가 `state`만이라, labels·priority·assignee 변경은 감지해놓고 진행 파일에 안 적혔습니다. 그러면 **다음 동기화에서 같은 변경이 또 감지됩니다.** 사용자는 아까 승인한 걸 계속 다시 승인하게 됩니다. 에러가 아니라 무한 반복이라 로그를 세로로 읽기 전엔 안 보입니다.

- **비교 기준값을 저장할 자리가 없었습니다.** 차이를 계산하려면 "직전에 내가 본 값"이 있어야 하는데, 그걸 담을 스키마 필드를 정의하지 않았습니다. 첫 동기화 이후로는 비교 기준이 없어서 **텍스트·구조 변경은 아예 감지가 안 되는 상태**였습니다.

**나머지 둘은 기능 누락입니다.**

- 제목·우선순위를 수동으로 고칠 경로가 없었습니다. Phase 전환 외에는 손댈 방법이 없었습니다.

- 이슈를 취소할 수 없었습니다. 종료 동작이 Done으로만 가서, 접은 작업도 완료로 기록됐습니다.

넷 다 고쳤습니다. 반영 대상 필드에 `labels`·`priority`·`assignee` 캐시를 추가하고, 스키마에 비교 기준값 블록을 정의하고, 이슈 속성 수정 동작을 하나 신설하고(동작 8개 → 9개), 종료 동작에 완료/취소를 고르는 파라미터를 붙였습니다.

돌이켜보면 앞의 둘은 **기능 테스트로는 절대 안 걸립니다.** 화면상 동작하고 에러도 없습니다. 한 번 돌려보고 "잘 되네" 하고 넘어갔으면 몇 주 뒤에 "왜 자꾸 같은 걸 물어보지"로 만났을 겁니다.

## 🚧 6. 플랫폼이 막는 것

설계로 못 넘는 벽도 있었습니다.

- **삭제 API가 없습니다.** Linear MCP에 이슈 삭제가 없어서 웹 UI로만 지울 수 있습니다. 자동화에서는 취소 상태로 보내는 게 최선입니다.

- **실시간 감지가 안 됩니다.** Claude Code에는 이벤트 루프가 없어서 webhook을 받을 수 없습니다. 팀원이 바꾼 즉시 아는 방법이 없습니다. 차선책으로 주기 폴링(`/loop 15m`)을 씁니다. 실시간이 아니라 "가끔 확인"입니다.

- **OAuth 토큰이 만료됩니다.** 만료되면 재인증이 필요한데, 이때 파이프라인 전체를 멈추면 안 됩니다. Linear 훅만 건너뛰고 개발은 계속 굴러가게, 동기화 실패는 경고 한 줄로 끝내도록 했습니다. 이슈 트래커 연동이 코드 작업을 막는 건 주객전도입니다.

마지막으로 밝혀둘 것이 있습니다. **여기까지는 샌드박스 검증이고 실제 팀 협업 운영이 아닙니다.** 로그의 "팀원 코멘트"도 외부 수정을 흉내 낸 것입니다. 4버킷 분류가 진짜 시험대에 오르는 건 여러 사람이 같은 보드를 동시에 만질 때인데, 그 데이터는 아직 없습니다.

## ✅ 7. 핵심 정리

- **문서보다 스모크 테스트가 빠릅니다.** `save_*` upsert, identifier 반환, 라벨 덮어쓰기는 다 직접 호출해서 알았습니다. 문서만 보고 설계했으면 전부 나중에 뒤집혔을 겁니다.

- **같은 API 안에서도 병합 규칙이 다릅니다.** `labels`는 덮어쓰기, 관계 필드는 추가입니다. 이 비대칭을 모르면 라벨은 조용히 지워지고 관계는 중복으로 쌓입니다.

- **자동 반영할 것과 사람이 볼 것을 나눠야 합니다.** 전부 자동은 위험하고 전부 수동은 피로합니다. 성격별로 4가지로 나누고, 기계적인 것만 자동 반영하되 승인은 묶어서 한 번만 묻습니다.

- **기능 테스트로는 안 걸리는 결함이 있습니다.** 감지하고 저장 안 하기, 비교 기준값 없기 — 둘 다 화면상 정상이고 에러도 없지만 다음 실행에서 조용히 반복됩니다. 로그를 세로로 읽어야 보입니다.

- **연동 실패가 본업을 막으면 안 됩니다.** 토큰이 만료되면 해당 훅만 끄고 개발은 계속 굴러가야 합니다.

| 상황 | 처리 |
| :---: | :---: |
| Phase 전환 시 라벨 갱신 | 전체 라벨 재구성 후 통째로 전달 |
| 팀원의 상태·우선순위 변경 | 일괄 승인 1회 → 반영 |
| 팀원의 본문·코멘트 변경 | 알림만, 파일 미변경 |
| 이슈가 차단됨 | 진행 즉시 중단 |
| 원격이 그대로임 | 해시 비교로 조기 종료 |
| 토큰 만료 | 해당 훅만 스킵, 파이프라인 계속 |
