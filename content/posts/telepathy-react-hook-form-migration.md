폼이 느리다는 느낌이 있었습니다. 입력값을 전부 `useState`로 들고 있으니 글자마다 리렌더가 날 테고, 그러면 React Hook Form으로 옮기는 게 맞겠다는 판단이었습니다.

그 판단이 맞는지부터 재봤습니다.

---

## 🔬 1. 먼저 재봤다 — 글자당 정확히 한 번

문제 구조 자체는 명확했습니다.

```
사용자가 'a' 입력
  → onChange → setUsername('a')
  → 상태 변경 → 컴포넌트 전체 리렌더
  → 자식(입력창 · 버튼 · 모달 등) 다시 계산
```

측정은 React DevTools Profiler로 했고, 옵션에서 **"Record why each component rendered"** 를 켰습니다. 원인을 제가 추측하지 않기 위해서입니다.

측정 환경에는 제약이 하나 있었습니다. 프로덕션 빌드는 프로파일링 정보가 제거돼 Profiler가 동작하지 않으므로 **개발 서버에서만** 잴 수 있습니다. 다만 리렌더 **횟수**는 개발·프로덕션이 동일하므로 횟수는 그대로 쓰고, 시간 값만 참고용으로 봤습니다.

폼 크기에 따른 차이를 보려고 가장 가벼운 폼과 가장 무거운 폼을 골랐습니다.

| 폼 | 상태 개수 | 입력 | 커밋 | 글자당 |
|----|----------|------|------|--------|
| 회원가입 (1회차) | 5개 | 12글자 | **12회** | 1.0 |
| 회원가입 (2회차) | 5개 | 12글자 | **12회** | 1.0 |
| 본인인증 | 9개 | 8글자 + 버튼 1회 | **9회** | 1.0 |

두 번 재서 둘 다 같았습니다. Profiler의 **"What caused this update?"** 가 각각 해당 폼 컴포넌트를 지목해서, 원인이 그 컴포넌트의 상태 변경이라는 것은 추정이 아니라 **React가 알려준 사실**이 됐습니다.

본인인증 화면은 인증번호 발송 후 3분 카운트다운이 1초마다 상태를 바꿉니다. 타이핑 기여분만 분리하려고 **발송 버튼을 누르지 않은 상태**에서 측정했습니다. SMS 실제 발송 비용과 발송 제한을 피하는 효과도 있었습니다.

## 🤔 2. 예상이 틀린 곳 둘

### 폼 크기와 리렌더 횟수는 무관했다

"상태가 많은 폼일수록 부담이 클 것"으로 예상했는데, 상태 5개 폼과 9개 폼이 **똑같이 글자당 1회**였습니다.

생각해 보면 당연합니다. 리렌더 횟수는 상태 개수가 아니라 **상태가 몇 번 바뀌는가**에 달렸고, 비용은 **컴포넌트 트리 크기**에 좌우됩니다. 두 폼 모두 트리가 작아서 차이가 나지 않았습니다.

### Context 연쇄 리렌더는 없었다

flame graph에서 렌더 경로는 18단계로 깊습니다.

```
WordSessionProvider → Context.Provider → BrowserRouter → Router
→ Navigation.Provider → Location.Provider → ModalProvider → Context.Provider
→ App → ThemeProvider → Context.Provider → IntentProvider → Context.Provider
→ AppRoutes → Routes → RenderedRoute → Route.Provider → [폼 컴포넌트]
```

그런데 **주황색으로 강조된 건 폼 컴포넌트 하나뿐**이고 상위 Provider는 전부 회색이었습니다. 상위가 함께 리렌더되지 않는다는 뜻입니다.

이건 다음 과제로 잡아둔 전역 상태 라이브러리 도입의 **근거를 약하게 만드는 관찰**입니다. 내 계획에 불리한 결과지만 그대로 적어두고, 해당 과제를 측정할 때 확인할 지점으로 남겼습니다.

## ⚖️ 3. 느리지 않았다, 그래서 근거를 다시 세웠다

한 커밋당 렌더 시간이 개발 기준 **1.6~3.8ms**였습니다. 60fps 예산인 16.7ms 안에 넉넉히 들어옵니다. 프로덕션은 더 빠릅니다.

**지금 타이핑이 버벅이지는 않습니다.**

여기서 "그래도 리렌더가 많으니 고쳐야 한다"고 쓰면 측정한 의미가 없어집니다. 대신 도입 근거를 바꿔 적었습니다.

> React Hook Form의 가치는 "현재 느린 것을 고친다"가 아니라
> **"폼이 커지거나 자식이 무거워져도 리렌더가 늘지 않는 구조"** 에 있다.

제어와 비제어의 차이는 이렇습니다.

| | 제어 (기존) | 비제어 (RHF) |
|---|---|---|
| 값 보관처 | React `useState` | **DOM 자체** |
| 타이핑 시 | 매 글자 상태 변경 → 리렌더 | **리렌더 없음** |
| 값 읽는 시점 | 항상 최신 | 제출 시 (`ref`로) |

`ref`로 DOM 입력값을 추적하므로 타이핑 중에는 React를 건드리지 않고, 글자당 리렌더가 0에 수렴합니다.

그리고 실제로 옮기기 시작하니, 성능보다 급한 것들이 먼저 나왔습니다.

## 🔍 4. 검증은 제출 핸들러에 뭉쳐 있었다

```ts
if (newPassword.length < 6 || newPassword !== confirmPassword) {
  setModalMessage('새 비밀번호를 다시 확인해주세요.');
  return;
}
```

길이 미달인지 불일치인지 구분되지 않는 **단일 메시지**였습니다. 사용자는 어느 입력창을 고쳐야 하는지 알 수 없었습니다. 게다가 오류를 모달로 띄우다 보니 두 가지 제약이 따라왔습니다.

- 모달은 한 번에 하나의 오류만 전달합니다. 아이디도 비어 있고 비밀번호도 약하면, **하나를 고친 뒤에야 다음 문제를 알게** 됩니다.
- 사용자가 모달을 닫아야 입력창으로 돌아갈 수 있습니다.

**중복 제출에도 무방비했습니다.** 네 개 페이지 모두 제출 진행 상태를 추적하지 않아, 네트워크가 느릴 때 버튼을 연타하면 요청이 누른 횟수만큼 발생했습니다. 회원가입·비밀번호 변경처럼 부수효과가 있는 요청에서 특히 위험했습니다.

**`form` 태그는 아예 없었습니다.** 전환 전 네 개 페이지의 `form` 개수는 0개였고, 버튼 `onClick`으로만 제출을 처리한 결과는 이랬습니다.

- 입력창에서 Enter 키를 눌러도 제출되지 않음
- 브라우저·비밀번호 관리자가 로그인/비밀번호 변경 폼으로 인식하지 못함 (`autoComplete` 속성도 0개)
- 로그인 화면에는 `type="submit"` 버튼이 있었으나, 감싸는 `form`이 없어 **아무 효과가 없는 상태**

## 🐛 5. 옮기다가 발견한 결함 둘

### 중복검사 결과가 낡은 채로 남는다

회원가입에서 아이디 중복검사를 통과한 뒤 아이디를 다른 값으로 수정해도 `isAvailable`이 `true`로 유지됐습니다.

```
"apple" 입력 → 중복검사 → 사용 가능 (isAvailable = true)
  → "admin" 으로 수정 → 중복검사 미실시
  → 가입하기 → isAvailable 이 true 라 통과
```

화면에도 "이 아이디는 사용 가능합니다"가 계속 떠 있어 사용자는 검증된 것으로 오인했습니다. **검사되지 않은 아이디로 가입 절차가 진행될 수 있었습니다.**

### 비밀번호 정책이 페이지마다 달랐다

| 페이지 | 규칙 |
|--------|------|
| 회원가입 | 8자 이상 + 영문/숫자/특수문자 중 2종 |
| 비밀번호 변경 | 6자 이상 |
| 비밀번호 재설정 | 6자 이상 |

8자 규칙으로 가입한 계정이 **비밀번호 변경을 통해 6자로 약화**될 수 있었습니다.

## 🛠️ 6. 채택한 것과 배제한 것

React Hook Form을 택한 이유는 `errors`(필드별 오류)와 `isSubmitting`(제출 상태)이 앞 절의 문제들을 **직접** 해결하기 때문입니다. 결함과 기능이 일대일로 맞물렸습니다.

반면 `zod` 같은 스키마 검증 라이브러리는 **도입하지 않았습니다.** 현재 검증 규칙의 복잡도가 내장 `rules`로 충분한 반면 번들은 늘어납니다. 해당 서비스는 gzip 압축이 아직 적용되지 않아 번들 증가에 민감한 상태였습니다.

### 선행 과제 — 공용 Input이 ref를 통과시키게

`register()`는 반환값에 `ref`를 포함하고, 이 `ref`가 실제 `input`에 도달해야 값이 추적됩니다. 기존 공용 컴포넌트는 `InputHTMLAttributes`를 확장하고 있어 `ref`가 타입에 없었고, spread로 흘려보내도 전달되지 않았습니다.

```diff
- interface AuthInputProps extends InputHTMLAttributes<HTMLInputElement> {
+ // React 19: ref 가 일반 prop → forwardRef 없이 타입 변경만으로 해결
+ interface AuthInputProps extends ComponentPropsWithRef<'input'> {
```

React 19에서 `ref`가 일반 prop이 된 점을 활용해 `forwardRef` 래핑 없이 **타입 변경만으로** 해결했습니다.

## 🧩 7. 검증과 오류 표시를 재구성

```ts
{...register('password', {
  required: '비밀번호를 입력해주세요.',
  validate: (value) => {
    if (value.length < 8) return '비밀번호는 8자 이상이어야 합니다.';
    const combo = [/[a-zA-Z]/, /[0-9]/, /[!@#$%^&*(),.?":{}|<>]/]
      .filter((re) => re.test(value)).length;
    return combo >= 2 || '영문/숫자/특수문자 중 2가지 이상을 포함해야 합니다.';
  },
})}
```

기존 `validatePassword`는 boolean만 반환해 **실패 이유를 전달할 수 없었습니다.** 통과 시 `true`, 실패 시 메시지 문자열이라는 규약에 맞추면서 이유별로 다른 메시지를 반환하도록 바꿨습니다.

필드 간 교차 검증은 `validate`의 두 번째 인자인 폼 전체 값으로 처리했습니다. `watch`는 값이 바뀔 때마다 리렌더를 유발하므로, **비제어로 옮긴 이점을 그대로 상쇄**합니다. 리렌더를 줄이려고 옮겨놓고 `watch`를 쓰면 앞뒤가 맞지 않습니다.

### 멀티스텝 폼은 인스턴스를 분리

비밀번호 찾기는 `step` 하나로 네 개 화면을 전환하는 구조였는데, 실제로는 성격이 다른 **두 개의 폼**(아이디 확인 / 비밀번호 재설정)이었습니다. `useForm`을 두 번 호출해 분리하고, 단계 간 전달이 필요한 값만 별도 상태로 승격했습니다.

하나의 폼으로 묶으면 단계 전환 시 언마운트된 필드의 값과 검증 규칙 처리가 설정에 따라 달라져 예측하기 어려워집니다.

### 오류 출처는 셋, 표시 경로는 하나

모달을 걷어내고 입력창 하단 인라인 표시로 통일했습니다.

| 출처 | 예시 |
|------|------|
| 검증 규칙 | `required`, `validate` 실패 |
| 서버 응답 (필드 특정 가능) | "이미 사용 중인 아이디입니다" → `setError('username')` |
| 서버 응답 (필드 특정 불가) | "로그인에 실패했습니다" → `setError('root')` |

로그인 실패는 서버가 아이디와 비밀번호 중 무엇이 틀렸는지 알려주지 않습니다. 보안상 의도된 설계이므로, 특정 필드에 붙일 수 없는 오류용으로 마련된 `root` 키를 사용했습니다.

### 규칙 객체 안의 onChange

앞서 본 중복검사 문제는 `register`의 **규칙 객체 안에** `onChange`를 등록해 값이 바뀌면 결과를 무효화하도록 해결했습니다.

```ts
{...register('username', {
  required: '아이디를 입력해주세요.',
  onChange: () => { setIsAvailable(null); clearErrors('username'); },
  validate: () => {
    if (isAvailable === false) return '이미 사용 중인 아이디입니다.';
    return isAvailable === true || '아이디 중복 검사를 완료해주세요.';
  },
})}
```

여기서 걸리기 쉬운 지점이 있습니다. JSX props로 `onChange`를 전달하면 **spread된 핸들러를 덮어써 폼이 아예 동작하지 않습니다.** JSX props는 객체 병합이라 같은 키는 뒤엣것이 이기기 때문입니다. 규칙 객체 안에 자리가 마련돼 있는 이유가 이것이었습니다.

## 📊 8. 결과와 남은 과제

| 항목 | 전환 전 | 전환 후 |
|------|--------|--------|
| `useState` 호출 (네 개 페이지 합) | 17개 | 4개 |
| `form` 태그 | 0개 | 5개 |
| `autoComplete` 속성 | 0개 | 10개 |
| 제출 중복 차단 | 없음 | 네 개 페이지 전체 |
| 오류 표시 방식 | 모달 (페이지당 1종) | 필드별 인라인 |

남은 `useState` 넷은 모두 **"사용자 입력값이 아닌 것"** 입니다. 회원가입의 중복검사 결과는 서버 응답이고, 비밀번호 찾기의 단계 값은 UI 상태입니다. 폼 값과 UI 상태를 분리하는 기준을 세운 결과입니다. 페이지는 넷인데 `form`이 다섯인 것도 같은 이유로, 비밀번호 찾기를 두 폼으로 나눴기 때문입니다.

사용자가 겪는 변화는 숫자보다 이쪽이 큽니다.

| 항목 | 전환 전 | 전환 후 |
|------|--------|--------|
| 오류 인지 | 어느 칸이 문제인지 알 수 없음 | 문제 칸 바로 아래 표시 |
| 동시 오류 | 하나씩 순차 노출 | 전부 동시 표시 |
| Enter 키 제출 | 불가 | 동작 |
| 비밀번호 관리자 | 인식 못함 | 저장·자동완성·변경 감지 |
| 네트워크 오류 | 미처리 (일부 페이지 무반응) | 인라인 안내 |

### 프론트엔드 밖으로 나간 것

작업 중 발견한 결함은 이슈로 문서화했고, 그중 하나는 범위를 벗어나 별도 과제로 분리했습니다.

> **서버에 비밀번호 강도 검증이 없습니다.** 서버는 값의 존재 여부만 확인하고 있어, API를 직접 호출하면 한 글자 비밀번호로도 가입이 가능합니다.

이 작업에서 가장 분명해진 게 이것이었습니다. **클라이언트 검증은 UX 수단이지 보안 수단이 아닙니다.** 화면에서 아무리 촘촘하게 막아도 요청을 직접 보내면 그만입니다. 공유 모듈에 규칙을 두어 양쪽이 같은 함수를 쓰는 방안을 후속 과제로 등록했습니다.

### 아직 못 한 것

**전환 후 리렌더를 아직 재지 않았습니다.** 제어에서 비제어로 옮겼으니 구조적으로 줄어드는 건 분명하지만, 재보기 전까지 "0에 수렴한다"는 말은 근거가 아니라 추론입니다. 앞에서 Before를 재놓고 After를 안 잰 채 개선했다고 쓰면, 재본 의미가 없어집니다.

측정 조건은 미리 적어뒀습니다. 같은 글자 수(회원가입 12글자), 같은 개발 서버, 그리고 **천천히 또박또박** 입력하기. 타이핑이 빠르면 React가 입력을 배치로 묶어 커밋이 줄어들기 때문에, 조건을 맞추지 않으면 개선된 것처럼 보일 수 있습니다.

나머지 둘도 적어둡니다.

- 비밀번호 검증 함수를 공용 모듈로 추출했으나 세 페이지 적용은 미완이라, **정책 통일은 아직 끝나지 않았습니다.**
- 이번 전환은 인증 관련 네 페이지만 다뤘습니다. 측정 대상이었던 폼 여섯 개 중 **둘은 아직 제어 컴포넌트**입니다.
