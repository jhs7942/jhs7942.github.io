[이전 편](/posts/react-compiler-local-mutation/)까지 컴파일러가 무엇을 자동화하는지 봤습니다. 그러면 당연한 질문이 나옵니다. **"useMemo·useCallback은 이제 레거시인가요? 싹 지울까요?"**

절반은 맞습니다. 습관적으로 뿌리던 `useMemo`·`useCallback`의 대부분은 이제 지워도 됩니다. 하지만 완전히 사라지진 않습니다. 이 훅들은 '잡부'에서 **'특수부대'로 승진**했습니다. 아무 데나 쓰이는 대신, 정말 필요한 곳에만 등장하는 정예 요원이 됐습니다. 컴파일러는 렌더링 **성능**을 책임지지만, 로직의 **정확성**과 참조 제어는 여전히 개발자의 몫이기 때문입니다.

---

## 🎖️ 1. 훅은 은퇴가 아니라 승진했다

관점을 바꿔야 합니다.

| | 과거 | 컴파일러 시대 |
| :---: | :---: | :---: |
| useMemo를 쓰는 이유 | 렌더링 성능(버벅임 방지) | 참조 안정성·의도 표현 |
| 사용 빈도 | 여기저기 습관적으로 | 소수의 결정적 지점에만 |
| 정체 | 잡부 | 특수부대 |

예전엔 "화면이 버벅이지 말라고" 훅을 썼습니다. 이제는 "데이터의 흐름을 끊거나 잇기 위해" 씁니다. 성능은 컴파일러에게 넘기고, 훅은 더 고차원의 역할로 이동했습니다.

---

## ⚓ 2. 참조 안정성 — 훅의 새 본질

핵심 개념은 **참조 안정성(referential stability)** 입니다. 변수가 불필요하게 흔들리지 않고, "내가 원할 때만" 바뀌도록 꽉 잡아 두는 것입니다.

배에 비유하면, 컴파일러는 배를 빠르게 나아가게 하는 **엔진**이고, `useMemo`는 배를 특정 위치에 고정하는 **닻**입니다. 엔진이 아무리 좋아도, 어떤 배는 파도에 휩쓸리지 않도록 닻을 내려야 합니다. 그 "닻이 필요한 배"가 이 편의 주제입니다.

자바스크립트에서 객체·함수는 만들어질 때마다 새 주소를 가집니다. `{ id: 1 }`과 `{ id: 1 }`은 내용이 같아도 다른 참조입니다. 이 참조가 언제 바뀌고 언제 유지되는지를 제어하는 것이 참조 안정성입니다.

---

## 🤖 3. 대부분은 컴파일러가 자동화한다

먼저 분명히 할 것이 있습니다. **참조 안정성 문제의 대부분은 컴파일러가 이미 해결합니다.** 컴파일러가 적용된 정상 컴포넌트에서는:

- **컴포넌트가 만드는 객체**가 자동 메모됩니다. `const options = { ... }`를 `useEffect` 의존성에 넣어도, 값이 같으면 참조가 유지돼 이펙트가 무한 재실행되지 않습니다.

- **JSX prop의 인라인 값**도 메모됩니다. `<Child data={[a, b]} />`의 배열도 `a`·`b`가 안 바뀌면 같은 참조로 넘어갑니다.

- **앱 내부의 커스텀 훅** 반환값도, 그 훅이 함께 컴파일되면 안정화됩니다.

그래서 예전에 "이 객체를 `useMemo`로 감싸야 이펙트가 안 터진다"며 넣던 코드의 상당수는 이제 불필요합니다. 컴파일러가 그 일을 대신합니다. **습관적으로 `useMemo`를 뿌리던 시대는 끝났습니다.**

이 사실을 모르고 자료들이 "Effect 의존성·외부 라이브러리 때문에 여전히 `useMemo`가 필수"라고 하면, 절반만 맞습니다. 정상 컴파일 구간에서는 자동 해결되기 때문입니다. 진짜 필요한 곳은 따로 있습니다.

---

## 🚁 4. 그래도 손이 필요한 경계

컴파일러가 **닿지 않는** 곳에서는 여전히 수동으로 씁니다. 세 경계입니다.

**① Bail-out된 컴포넌트(Escape Hatch)** — [2편](/posts/react-compiler-pipeline-rules/)에서 봤듯, 규칙 위반이나 `"use no memo"`로 컴파일러가 최적화를 포기한 구간이 있습니다. 건드리기 무서운 레거시나 복잡한 변환 로직입니다. 여기선 무거운 연산을 사람이 방어합니다.

```jsx
// 컴파일러가 손 뗀 컴포넌트 — 무거운 연산은 수동 useMemo로 방어
function LegacyChart({ rawData }) {
  const processed = useMemo(() =>
    rawData.filter((d) => d.isValid).map(complexTransform),
  [rawData]);
  return <Highcharts data={processed} />;
}
```

**② 컴파일러 밖의 값 — 배포용 라이브러리 훅** — 컴파일러는 컴파일하는 코드 안에서만 왕입니다. npm에 배포하는 공용 훅은 소비자 환경의 컴파일러가 그 내부까지 컴파일하지 않을 수 있습니다. 그래서 **라이브러리로 내보내는 훅**은 반환값의 안정성을 스스로 보장해야 합니다.

```jsx
// 배포용 훅: 소비자가 반환값을 deps에 넣을 수 있으니 직접 안정화
function useSearch(query) {
  const [results, setResults] = useState([]);
  const search = useCallback(async () => {
    setResults(await api.search(query));
  }, [query]);
  return useMemo(() => ({ results, search }), [results, search]);
}
```

> 주의: 이건 **배포용·공용** 훅 이야기입니다. 여러분 앱 안에서만 쓰는 커스텀 훅은 컴파일러가 함께 컴파일하므로 이렇게 감쌀 필요가 없습니다. "소비자가 어떻게 쓸지 모르는" 경계에서만 의무가 됩니다.

**③ 리액트 밖 라이브러리와의 소통(Interop)** — Mapbox·D3·Chart.js·Three.js는 리액트 컴파일러의 존재를 모르고, 보통 `prev === next` 참조 비교로 갱신을 판단합니다. 정상 컴파일 구간이면 JSX prop 값이 자동 메모돼 대개 안전하지만, 라이브러리가 그 값을 내부에 저장해 두거나 조건부로 생성되는 값이면 참조가 흔들려 지도가 깜빡이거나 리셋될 수 있습니다. 이런 민감한 경계에는 **명시적으로** 닻을 내려 둡니다.

```jsx
function MapComponent({ lat, lng }) {
  // 외부 지도 라이브러리에 안정적 참조를 보장
  const center = useMemo(() => [lat, lng], [lat, lng]);
  return <GoogleMap center={center} />;
}
```

## 📝 5. useMemo는 코드에 남기는 의도

이제 `useMemo`를 바라보는 눈이 달라집니다. 성능 수치를 깎는 도구가 아니라, **의도를 남기는 주석**에 가깝습니다.

- **과거(기술자)** — "렌더링 횟수를 줄이려고 훅을 쓴다."

- **현재(설계자)** — "이 데이터의 생명 주기와 영향 범위를 정의하려고 훅을 쓴다."

컴파일러 시대에 명시적으로 남긴 `useMemo`는 동료에게 이렇게 말합니다. **"이 값은 외부 시스템과 연결됐거나 컴파일러가 못 미치는 민감한 녀석이니, 참조를 함부로 바꾸지 마세요."** 자동 조종(컴파일러)이 90%를 처리하지만, 난기류(bail-out·interop·컴파일러 밖)에서는 조종사가 개입합니다. 도구에 의존하는 게 아니라 도구를 통제하는 것입니다.

---

## ✅ 6. 핵심 정리

- **대부분의 `useMemo`·`useCallback`은 사라집니다.** 컴파일러가 컴포넌트 객체·JSX prop·앱 내부 훅 반환을 자동 메모하므로, 습관적으로 뿌리던 최적화 코드는 지워도 됩니다.

- **훅은 성능 도구에서 참조 안정성 제어 도구로 승진했습니다.** 이제 "화면 버벅임 방지"가 아니라 "데이터 흐름을 원할 때만 바꾸기"를 위해 씁니다.

- **손이 필요한 곳은 컴파일러 경계 밖입니다.** ① bail-out된 컴포넌트(escape hatch), ② 배포용·공용 라이브러리 훅, ③ 리액트 밖 라이브러리와의 민감한 interop.

- **명시적 `useMemo`는 의도의 주석입니다.** 성능 수치가 아니라 "이 참조는 건드리지 말라"는 설계 의사를 코드로 남기는 것입니다.
