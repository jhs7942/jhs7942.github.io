싸피 마이스터고 트랙은 총 12회 AI 시험 중 5회 과락 누적 시 강제 퇴소인 구조입니다. 본인은 6회차 시점 과락 0/5로 여유가 있었지만, 반 친구들 다수가 과락 위기였고 각자 NotebookLM으로 개인 퀴즈를 만들어 풀고 있었습니다. 같은 시험 범위를 1,000명이 각자 만드는 중복 낭비를 목격한 게 시작이었습니다.

시험까지 이틀, 실사용 기간을 고려해 기획·배포를 포함한 개발 기한을 4시간으로 잡았습니다. Vite·Supabase는 이 프로젝트가 첫 사용이었고 Claude Code도 누적 1개월 차 — "AI 도구가 숙련도 공백을 메울 수 있는가"를 건 도박이었습니다.

서울 15기 1,000명 대상 기획이 부산·광주 등 전국 캠퍼스로 유기적 확산됐고, 2주간 실사용 지표를 보며 개선했습니다.

제약 안에서 기술을 고르기 — LLM 대신 정적 JSON 범위 적합도 ↑ ▼
문제
  • 시험 범위가 싸피 내부 교재로 고정돼 있었습니다. 문제를 무한히 만들 수 있어도 범위를 벗어나면 무용지물입니다.
  • 4시간·Claude Code Pro 토큰 한도 안에서 무엇을 만들지보다 무엇을 안 만들지를 먼저 정해야 했습니다.
해결

검토한 선택지

A. LLM 동적 생성무한 확장이 가능하지만 시험 범위 적합도를 구조적으로 보장할 수 없어 구상 단계에서 기각했습니다(API 미구현).
B. 교재 기반 JSON (채택)생성형 AI 초안 + 인간 검수 하이브리드로 범위 완전 일치·즉시 응답·비용 0원을 모두 확보했습니다.
C. 순수 수동 작성품질은 가장 높지만 4시간 데드라인 대비 시간 효율이 낮아 기각했습니다.

실측 근거

  • v1 LLM 샘플 검수: 30개 중 1개 오류. 오류 유형이 품질 저하가 아니라 "범위 이탈"이었다는 점이 교재 기반 우위를 확정했습니다.
  • 하이브리드 파이프라인(전사 → NotebookLM 초안 → 팀원 2명 검수)으로 1차 시험용 930문제를 약 2시간에 생성·검수했습니다.

해결

사전 설계형 — silent fail

  • 문제 데이터는 정적 JSON을 필수로, Supabase는 분석·로깅 전용 선택으로 구조를 나눴습니다. 모든 Supabase 호출을 silent fail로 처리해 DB가 죽어도 문제 풀이 자체는 죽지 않도록 했습니다.
  • 재시도·미들웨어가 아니라 "JSON=필수, DB=선택"이라는 구조 자체가 가용성을 만든다고 판단했습니다.

학습형 — RLS 전면 비활성화

  • 익명 키(anon key)로 401 에러를 겪은 뒤, SELECT 정책 / return=minimal / 클라이언트 UUID / 전면 비활성화 4개 대안을 검토했습니다. "anon key + PII 없음 + 공개 데이터"라는 Context에서 RLS 본래 목적이 애초에 적용되지 않는다고 판단해 전면 비활성화를 택했습니다.
결과
  • 운영 기간 중 DB 장애 시에도 퀴즈 풀이 기능 무중단 — 사전 가설 확증.
최적화 대신 롤백 — 정량 근거로 "안 하기"를 정당화 한도의 10% 미만 ▼
문제
  • 이벤트마다 즉시 저장하던 배치 호출을 모아서 보내는 최적화가 필요한지 판단해야 했습니다. 직감이 아니라 근거가 필요했습니다.
해결

두 근거 모두 한도의 10% 미만이라, 스스로 정한 최적화 도입 기준(30%)에 한참 못 미쳐 배치 저장을 롤백했습니다.

결과

해결

즉시 확정한 Anti-scope

  • UI 프로토타입·디자인 평가 에이전트 미사용 (기능 완성 > 디자인)
  • 기기 간 진도 동기화 미구현 (로그인 복잡도 회피)
  • PWA 미도입 확정 — Vite 8 peer dependency 실패 후 반응형 웹으로 대체
  • 문제당 정답률 표시 삭제 — 본인이 UX 오버헤드라 판단해 주도적으로 반대

협업 인프라 부재의 대가 — 팀원 소외감 ▼
문제
  • 코드는 본인 1인, 콘텐츠 제작·검수는 팀원 2명이 분담했습니다. 4시간 중 가장 오래 걸린 건 구현이 아니라 팀원과의 요구사항 협의 — "무엇을 안 할지 정하는 과정"이었습니다.
  • 업무 분배를 가시화할 협업 툴 없이 진행하면서, 콘텐츠 팀원 2명이 업무 분배 불균형으로 소외감을 느꼈고 진로 고민까지 갔습니다. 프로젝트 종료 후 회고에서야 깨달았습니다.
해결

이 프로젝트에서는 즉시 대응하지 못했습니다. 같은 패턴이 후속 프로젝트(텔레파시 전신인 how_many)에서 신규 팀원 2명 이탈로 반복된 뒤에야, 이탈한 팀원이 다른 프로젝트에서 활약하는 모습을 보며 "내가 사람을 잃게 만들었다"는 책임을 체감했습니다.

결과
  • 이후 모든 프로젝트에서 Linear 기반 테스크 분배를 첫 30분에 세팅하는 것을 기본값으로 삼았습니다 — "협업 도구는 속도의 반대가 아니라 속도의 전제"라는 인식 전환입니다.
